# agents.md — 单并发本地推理约束（配合 dsh-subagent-serializer 插件）

> 说明：本模板与 `dsh-subagent-serializer` 插件配合使用。
> 插件负责**硬约束**（子代理延迟启动 + 强串行），本文件负责**软约束**（引导主代理行为）。
> 把下面内容复制到你的 agents.md（会话指令 / 工作区指令）中。

## 单并发推理纪律（必须遵守）

本环境的本地推理引擎**同一时刻只能处理一个请求**。主代理与子代理并发生成会导致上下文反复加载切换、响应极慢。你必须严格遵守以下规则：

### 1. 一次只派发一个子代理

- 会话中**同时最多只能有一个子代理在运行**。
- 在派发下一个子代理之前，必须先等当前子代理完成并把结果回传。
- 不要同时启动多个 `subagent` / `subagent_fork` / `team_delegate` 调用；即使它们看起来相互独立，也要串行执行。
- 插件会把上述三种工具（以及你配置进 `toolNames` 的其他委托工具）统一串行 + 延迟启动。

### 1b. 唤醒消息（send_message）同样受控

- `send_message` 唤醒 inactive 子代理会触发它的推理，与启动新子代理同等对待：
  - 插件会让 `send_message` **等引擎空闲后**再投递（同样有延迟）。
  - 你仍然要遵守"一次只唤醒一个"——不要同时向多个子代理发送唤醒消息。
- 已完成的子代理不需要唤醒；先 `list_agents` 确认目标状态再决定。

### 1c. 中断（interrupt_agent）立即生效

- `interrupt_agent` 是停止操作，插件让它**立即执行**（不做延迟/排队）。
- 中断某个子代理后，它结束时会释放并发槽位；在那之后你才能派发新的子代理。

### 2. 派发后立即停止工作

- 一旦调用 `subagent` / `subagent_fork` / `team_delegate` 工具，**你（主代理）必须立刻停止一切工作**：
  - 不要继续调用其他工具；
  - 不要继续生成新的推理请求；
  - 不要做任何会触发推理引擎工作的操作。
- 插件会让子代理延迟启动（默认 30 秒），这段时间是你的"收尾缓冲"：尽快结束当前回合，把控制权交还，等待子代理完成。

### 3. 子代理完成后才恢复工作

- 子代理完成并把结果回传给你之后，你才可以继续工作。
- 继续工作后，如再次需要派发子代理，重复上述规则（先等前一个完成，再派下一个）。

### 4. 使用前台模式（推荐）

- 派发子代理时优先使用前台模式（`run_in_background: false`），让主代理阻塞等待结果，天然符合"派发后停止工作"。
- 确需后台/continuable 模式时，更必须遵守第 2、3 条，否则主代理与子代理必然并发冲突。

### 5. 排队是预期行为

- 若你的子代理调用显示"排队等待空槽"或"引擎忙，等待空闲"（插件日志），说明前一个子代理尚未结束、或引擎正在处理当前请求。这是正常现象，不要重试或并发加塞，耐心等待放行。
- 插件会探测引擎（`/props`）自动确认并发数，并在引擎空闲（`/slots` 无处理中槽位）后才放行子代理——这是为了不让子代理挤进引擎的 FIFO 排队、反复切换上下文。

---

## 为什么需要这些规则

- 本地引擎单并发：主代理生成 + 子代理生成 = 两个请求同时到达 = 引擎来回切换上下文 = 超级慢。
- 插件只保证"子代理之间"不并发；"主代理 vs 子代理"的并发只能靠你（模型）遵守本约束来避免。
- 遵守本约束后，任何时刻引擎都只处理一个请求，速度恢复单并发应有的水平。
